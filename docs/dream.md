# Dream 产品 Spec

状态：产品行为及精简版模型可见文案已于 2026-10-04 获用户批准，已实现。

## 1. 产品目标

把固定每周一次的 Weekly 整理，改为每天检查、有材料才启动的 Dream。
让 Mochi 更及时地连接最近生活与已有认识，也能把值得以后再想的事情留给未来的自己。

Dream 不是每天必须产出总结、修改 Core 或主动联系 user 的任务。
“看过以后决定保持原样”是正常完成，不以修改数量衡量效果。

## 2. 本次范围

| 本次做 | 本次不做 |
|---|---|
| 用 Dream 替代 Weekly，保留一条 Main 整理路径 | 不让 Weekly 和 Dream 并行运行 |
| 每日检查、材料累计、最长等待兜底 | 不每天无条件调用 Main |
| 持久化整理进度，未展示完的材料留待以后 | 不全量重跑历史，不改写原始对话 |
| 沿用 Core、Memory、关系图现有整理能力 | 不扩展通用知识图谱或改变记忆事实边界 |
| 接入现有 Self Reminder 的查看、创建、修改和取消 | 不新增提醒调度器，不允许 Dream 操作 notify 提醒 |
| 保留现有文字相关的旧记忆对照 | 本次不升级向量检索、不新增自动经历库、记忆休眠或遗忘机制 |

Nightly 继续负责日切、保留期清理等确定性维护，不调用模型。
普通聊天、睡前回顾、Free Time 和日初日记回望的职责不变。

## 3. 什么时候做梦

### 每日机会

- 沿用现有夜间维护时间、时区和逻辑日。当前代码默认整理检查时间为 03:15，不为了与私人实例一致而另设一个 03:30 定时器。
- 当日 Nightly 成功后检查 Dream；检查材料数量和进度本身不调用 Main、Lite 或 Embedding。
- 有活动聊天或睡前过渡时暂缓，不抢占聊天，也不因此消耗当天的 Main 启动机会。
- 暂缓或服务重启后，允许在当天后续空闲时检查；只处理当前逻辑日的机会，不按错过的天数补跑。
- 每个逻辑日最多启动一次 Dream Main。一次 Dream 可以包含多轮模型与工具调用，不等于只计费一次。
- 普通聊天在 Dream 期间到来时，聊天优先；Dream 不再发起后续模型或工具步骤。已提交的操作保留，未完成的批次留待下一日。已经发出的模型请求不承诺能取消计费。

### 累计与兜底

满足下列任一条件才启动 Main：

1. 有上次失败、中断或因单次预算未读完的待续材料。
2. 新增待整理材料达到 8 个计数单位。
3. 有待整理材料，且距离上次成功整理已满 7 个逻辑日。

没有材料时不启动，不能仅因过去了 7 天而空跑。
“7 天”是正常可运行条件下的触发兜底，不是停机、持续失败或超大积压时的清空时限。

### 什么算材料

| 内容 | 是否累计 |
|---|---|
| 一条新增 Memory Item | 计 1 |
| 同一条 Memory 的内容或来源证据发生外部更新 | 当前尚未整理的版本计 1，不按编辑次数重复加分 |
| 一天已归档、含 Main 自写正文的日记 | 计 1；同一天分段读取不重复计数 |
| 空日记、只有自动状态栏的日记 | 不计 |
| Core、旧记忆对照、关系图、自我提醒及其执行结果 | 作为判断背景，不作为新增材料累计 |
| 访问次数、索引更新、单纯 importance 调整 | 不计 |
| Dream 自己创建或整理的记忆与其他输出 | 不作为下一次 Dream 的新材料；后续外部的新内容或新证据仍可再次进入 |

这里的“8”只是调用节奏，不是重要程度评分。
代码不按情绪词、话题关键词或猜测的重要性决定哪些生活值得 Main 思考。
尚未完成现有提取流程的聊天不假装已经成为 Memory；Dream 不额外启动 Lite 抽取。

## 4. Main 看见什么

每次 Dream 使用同一个 Main 和当前 Core，不建立另一套夜间人格。
模型可见文字使用 user 指代对话对象，不预设主从关系或额外身份称呼。

- 尚未整理的新记忆、它们可见的用户消息证据，以及相关旧记忆。
- 尚未读完的已归档日记正文，保留逻辑日期；日记是 Main 的表达与理解，不自动成为客观事实证据。
- 当前关系图，仍遵守现有用户生活关系与来源证据边界。
- 待触发的 Self Reminder，以及近期已处理提醒的真实结果，避免只记得安排、不知道后来是否执行。
- 同一待续批次先前已经完成、失败或结果未明的操作回执。

不额外加入聊天路由、自动召回或第二次 Lite 总结。
证据所需的原始消息沿用现有受限读取，不把整段普通聊天上下文重复装入 Dream。
Admin evidence 始终只给人看，不进入 Dream；Main 的操作连续性来自正式执行记录。

初始单次材料预算沿用现有量级：最多 40 条待整理记忆、40 条相关旧记忆、
12,000 字符的归档日记；额外提供最多 20 条待触发自我提醒和 10 条近期处理结果。
每类都说明实际数量、总量及是否截断，不把没看见的内容描述成“没有”。

## 5. 整理进度如何保真

材料按从旧到新的顺序进入受限批次，不再每次只取最近一周的最新条目。
记忆与日记分别保留进度；日记超过预算时保留读到的位置，不能跳过整天剩余正文。

只有完整提供给 Main 的记忆版本、实际提供的日记片段，才进入本次可推进范围。
一次正常完成可以推进这部分材料，即使 Main 没有做任何修改；这只表示已提供判断机会，
不是声称模型逐条理解正确。

运行期间新增或改变的材料仍然待处理。整理自己的写入与外部更新必须区分，
不能单凭 `updated_at` 变化反复唤醒，也不能只按新 ID 而漏掉旧条目的新证据。

首次启用以最近 7 个完整逻辑日内的材料，加上当前逻辑日已经提交的材料，作为有限起点。
更早的记忆仍能作为相关旧记忆被带入，不会被删除或标成“历史都已整理完成”。
这次不做全量历史补课，也不声称能够重建旧 Weekly 没有记录过的审阅进度。
起始材料非空时，建立首批并在下一次可用的日机会整理；完成后开始正常累计。
起始材料为空且尚无成功记录时，从首次出现待整理材料的逻辑日开始计算 7 日兜底。

## 6. Main 可以做什么

| 能力 | 产品边界 |
|---|---|
| 整理 Core | Main 自主决定是否提交完整修订；保留可见版本校验和快照。不强迫每天更新，也不自动膨胀 Core。 |
| 整理 Memory | 沿用现有创建、编辑、合并、归档，以及来源证据、回收站、索引一致性规则。 |
| 整理关系图 | 沿用人物、宠物、地点和现有关系词汇；Core 与日记不能单独充当事实证据。 |
| 管理 Self Reminder | 可创建未来意图，也可修改、取消当前可见且尚未开始处理的 self 提醒；不能操作直接通知 user 的 notify 提醒、Todo 或已经执行中的提醒。 |
| 什么都不改 | 正常、可成功结束；没有规定必须使用哪项能力。 |

Core 与整理工具原来的“每周一次”执行回执改为绑定实际 Dream 批次，
防止同一批重试重复提交，而不是整周锁住后续 Dream。
关系工具直接使用当前可见证据，不要求先执行空的 Memory 操作。
Memory 修改后刷新可见关系证据，Main 可以在下一轮基于新状态继续整理关系。

Self Reminder 保存的是未来重新判断的意图，不是预写给 user 的通知。
到点后走现有 Self Reminder 路径，由当时的 Main 决定行动、开口或安静结束，
继续遵守现有五分钟有效期与送达边界。

Dream 当场不发文字、图片或其他消息，不开放普通聊天的全部工具或按需升级工具权限。
它的最终文字不写成用户消息、聊天回复、新记忆或第二份“梦境报告”。

## 7. 失败、重试与成功

- 完整的 Main 正常终态才可能完成批次；超时、截断、工具轮数耗尽和未解决的工具执行失败不能被记成成功。
- 失败或中断不推进本批材料进度；当日已经启动过 Main，就留待下一逻辑日，不进入高频重试。
- Core、Memory、关系和提醒不承诺跨文件、跨表的一次全局事务。每项操作保留现有原子性，并记录真实结果。
- 已经完成的操作不回滚，也不因批次重试而自动重放；尤其不能重复创建相同操作对应的 Self Reminder。
- 继续整理前提供已执行回执和当前目标版本。发现并发变化时重新读取并由 Main 判断，不覆盖用户或其他入口的新改动。
- 上次尝试失败，不等于未来 Main 必须机械完成旧动作。下一次可以重新判断并零修改结束，历史失败记录仍保留；不从最终文案猜测某个操作“恢复成功”。

批次“完成”不等于“写入过内容”，也不等于“已经联系 user”。

## 8. 开关、可见性与成本

保留一个 Dream 开关，替代 Weekly 的产品入口，不额外增加一排策略开关。
切换时保留用户原来的维护启停选择、实际时间和全部数据，不因名称变化恢复默认开启。
关闭 Dream 只停止后续整理，不删除记忆、进度或已经安排的 Self Reminder。
Admin 偏好中显示 Dream；存储仍沿用 `WEEKLY_MAINTENANCE_ENABLED` 与
`WEEKLY_MAINTENANCE_MINUTE`，不迁移原配置，也不保留第二条周调度实现。

现有维护记录中应能看到：未启动的原因、待整理数量、最后成功时间、
本次是否有剩余材料，以及失败或中断的真实状态。
沿用现有用量和执行诊断入口，不新增一个 Dream 仪表盘，也不把诊断结果注入 Main。

活跃期间可能一天一次，Main 总费用可能高于每周一次。
Dream 单轮输出上限为 8,192 token，包含推理模型的思考消耗；
这是 2026-10-04 首次 Test 运行被 4,096 token 上限截断后获批的专属预算，
不改变普通聊天上限或关闭 Main 思考。上限不是实际每次消耗。
安静时期只做本地检查；不增加一个固定的每日 Lite 或 Embedding 调用。
Self Reminder 日后唤醒 Main 的费用也属于真实成本，不算进“检查零调用”里。

## 9. 产品验收场景

| 场景 | 预期结果 |
|---|---|
| 连续几天无新材料，仅有自动状态更新 | 不启动 Dream Main |
| 两天累计 5 + 3 条待整理记忆 | 第二次日检查达到门槛；不必等周一 |
| 少量材料一直不足 8 个单位 | 满足 7 个逻辑日兜底后启动，不无限等待 |
| 一次积累 85 条记忆 | 首次最多提供 40 条，后续每日机会继续 40、5；最后 5 条虽不足门槛，仍属于待续任务 |
| 一天日记超过 12,000 字符 | 明确本次片段与剩余；成功后下一次从未读位置继续，不整天跳过 |
| Main 看过以后决定不修改 | 批次正常完成；相同材料不因零修改反复触发 |
| Dream 合并、创建或调整自己的记忆 | 不把自己的整理成果再累计成新生活 |
| 整理过的旧记忆获得新来源证据 | 新版本重新成为待整理材料 |
| 创建 Self Reminder 后本次超时 | 提醒保留；下次可见真实回执，不重复创建 |
| 截断、轮数耗尽或真实执行失败 | 状态不是成功，进度不越过未完成批次 |
| user 的聊天到来或 Core 被其他入口修改 | 聊天优先；已完成操作保留；旧版本不能覆盖新 Core |
| 重启服务 | 保留当日启动记录、批次进度与已完成操作，不重画当天机会 |

确定性逻辑用现有相关测试扩展覆盖；真实模型的工具可用性、静默运行和提醒接续，
在代码交付到 MochiBot Test 后验证。不以模型文案是否命中或修改次数作为断言。

## 10. 审批与实施边界

本 spec 审批的是产品行为，不替代模型可见文字的逐字审批。
本次精简稿已完成逐字审批；后续新增模型可见文字仍需另行展示具体文本或 diff。
本提案不修改私人 Mochi，不部署朋友实例，也不包含 release 授权。
